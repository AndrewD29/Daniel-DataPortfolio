NPS All-in-One Dashboard

Power BI DAX Power Query Forecasting Regression

Situation

A client was rolling out a new third-party NPS (Net Promoter Score) survey tool to capture customer feedback on brand loyalty and likelihood to recommend, but had no way to view performance broken down by Department, Team Leader or Agent.

Task

Build an interactive "All-in-One" (AIO) Power BI dashboard giving every level of the client's hierarchy visibility of their NPS performance, with an email-screenshot fallback via Power Query for anyone without direct Power BI access.

Action

Before any dashboard work could start, the survey data needed enriching — it had no link back to which agent handled each call or how that call went. I sourced and joined internal telephony data to the survey export (matching on caller ID and call timing, since there was no shared key), validated the match at 92% accuracy against a 100-call manual sample, and added a keyword-search flag to catch dropped-call verbatims. Full detail on that data pipeline is on the SQL Projects page.

With a clean, joined dataset, I set up a shared OneDrive folder as the ingestion point so the model would future-proof itself — any team member could drop a new extract in and Power BI would pick it up. In Power Query, I promoted headers, corrected date/time typing, renamed columns for clarity, and added conditional columns to convert text ratings into numeric scores: 

= Table.AddColumn(#"Renamed Columns", "CSS Score", each
    if [CSS] = "V. Satisfied" then 100
    else if [CSS] = "Satisfied" then 75
    else if [CSS] = "Neutral" then 50
    else if [CSS] = "Dissatisfied" then 0
    else if [CSS] = "V. Dissatisfied" then 0
    else null)

Once the model was in place, I built three views tailored to different audiences:

  • Department Summary — NPS and CSS gauge charts against target lines, an FCR donut, and a top-level slicer.
  • Team Manager view — CSS as a month-on-month bar chart, an NPS gauge, an FCR donut, and slicers for team and week commencing.
  • Agent CSS view — a ranked table (score, NPS, FCR, survey count, dropped-call count) built on new DAX measures, plus a verbatim comments table with score filtering.
Rank = RANKX(
    ALLSELECTED('Survey (All)'[Agent Name]),
    CALCULATE(SUM('Survey (All)'[CSS Score])),
    , DESC
)

FCR Score = DIVIDE(SUM('Survey (All)'[FCR Score]), SUM('Survey (All)'[FCR Count])) * 100

Following stakeholder review, two extra requests came in: a CSS score forecast, an AHT (Average Handling Time) forecast, and two correlation checks — survey volume vs. score, and agent knowledge/expertise vs. NPS.

For CSS, I used Power BI's built-in forecast visual (5-month horizon, 90% confidence per the client's spec) and held back the last month of actuals to visually validate forecast accuracy. For AHT — built in Excel during a Power BI outage — I used exponential smoothing: 

Forecast: =FORECAST.ETS(A17, $B$2:$B$16, $A$2:$A$16, 1, 1)
Lower: =E17-FORECAST.ETS.CONFINT(A17, $B$2:$B$16, $A$2:$A$16, 0.95, 1, 1)
Upper: =E17+FORECAST.ETS.CONFINT(A17, $B$2:$B$16, $A$2:$A$16, 0.95, 1, 1)

For the correlation work, I used Power BI's Correlation Coefficient quick measure alongside RMS Error and a P-value, rather than relying on a scatter chart alone — the visual pattern for survey volume vs. CSS looked ambiguous, and the statistics confirmed it wasn't a real relationship. For knowledge/expertise vs. NPS, the same approach confirmed a genuine one, and I calculated the regression coefficient to show the client the expected NPS gain per point of knowledge-score improvement.

Result

R² = 0.51 Knowledge score vs. NPS (confirmed)
R² = 0.16 Survey volume vs. CSS (rejected)
5.4 pts est. NPS gain per knowledge-score unit

The published dashboard gave the client self-serve visibility across Department, Team Leader and Agent levels for the first time. The regression findings were the standout outcome — they ruled out survey volume as a lever worth chasing and instead gave the client's training team a concrete, quantified case for investing in agent knowledge and expertise. The AHT forecast was picked up by the planning team for further development, extending the reach of the work beyond the original brief.

Anonymous Agent Dashboard

Power BI DAX Row-Level Personalisation Data Modelling

Situation

While monitoring performance, I noticed dips at agent level that weren't showing up in the overall numbers. A conversation with team managers surfaced a separate, related problem — they were struggling to pull all the data they needed for performance reviews and 1-2-1s into one place, relying on manual admin across multiple sources.

Task

Build an agent-level dashboard pulling together the relevant sources from our data catalogue — SAP (B04), AWS, Neqqoo and Qualtrics — that would give agents visibility of their own performance against target and give managers a single, accurate source for reviews.

Action

I started by scoping the available data for quality and completeness, then ran SME sessions to confirm the sources and approach were feasible and get buy-in before building. Data was brought into Power BI via SharePoint so it would refresh continuously without disrupting the live dashboard, with relationships between sources kept to many-to-one or one-to-one wherever possible to limit the risk of data errors.

Design was deliberately made engaging rather than a flat table — after confirming required KPIs with team managers, I built a month-on-month view so agents could see their own progression. When a second department needed adding, I used a grouping table so the same visual could dynamically swap which KPI set it displayed based on department selection, rather than duplicating pages: 

Table Change = {
    ("% Sales Conversion", NAMEOF('AWS - Agent'[% Sales Conversion]), 0),
    ("TCHT", NAMEOF('AWS - Agent'[TCHT]), 1),
    ("Avg Hold Time", NAMEOF('AWS - Agent'[Avg Hold Time]), 2),
    ("Avg Wrap Time", NAMEOF('AWS - Agent'[Avg Wrap Time]), 3),
    ("Transfer %", NAMEOF('AWS - Agent'[Transfer %]), 4),
    -- ...additional KPI mappings for the second department's metric set
}

The key design requirement was accountability without exposing colleagues' performance to each other. I hid agent identities behind a generated index, then used a measure keyed off the signed-in user's principal name so only the viewer's own row would resolve to a real name — everyone else's row in the comparison stayed anonymised: 

Employee Hidden ID = "User" & [EmployeeIndex]

Current User =
IF(
    [TCHT] && SELECTEDVALUE('Verint - Agent Activity - Grouped'[PNumber]) = USERPRINCIPALNAME(),
    SELECTEDVALUE('Verint - Agent Activity - Grouped'[Employee Name])
)

That let each agent see exactly where they stood against the wider team without turning the dashboard into a public leaderboard.

Result

After SME and team manager sign-off, the dashboard was published to the full agent population, with team managers running training sessions to introduce it since Power BI was new to most of that audience. It remains in active use, giving agents direct ownership of their own performance data for the first time.

FCA Conduct Risk Dashboard

Power BI Power Query Regulatory Reporting RAG Status

Situation

As an FCA-regulated business, we needed a clear, defensible way to demonstrate monthly adherence to contractual KPIs — for internal senior management and for the regulator itself.

Task

Produce a dashboard robust enough to withstand scrutiny from senior management and regulatory bodies, starting with the telecommunications part of the business.

Action

I set up an automated export of the source data from SAP (B04) into a secure SharePoint location to remove manual steps that could introduce errors, then optimised the Power Query load to keep the report fast — trimming to only the columns needed, filtering the date range to the last 3–6 months, and pushing transformations back to the source via query folding where possible rather than processing them in Power BI.

Every KPI was validated in a table before going live: any figure that looked abnormal was traced back to either a measure (checked against the supplied calculation documentation) or a column (checked for formatting and source issues). Conditional RAG (red/amber/green) formatting was then applied across the board for an at-a-glance achieved/missed view, with Country, Site and Department slicers and three headline KPI cards showing month-on-month movement.

Once live, two other business areas — Energy and Broadband — asked for the same treatment, having previously tracked this manually in Excel. Building it directly in Power BI ran into a data-access constraint (analysts are restricted to the clients they work on), so as an interim solution each analyst updated a shared Excel sheet that Power BI then pulled in — agreed as a stop-gap until the underlying access/security question could be resolved properly. With three companies now in one dashboard, I added a front page with navigation buttons per business area, and a Thresholds table (KPI, target, client vs. self-measured, and consequence of a miss) to make the "why" behind each RAG rating transparent to reviewers.

Result

The dashboard was rolled out across all three regulated business areas in a single, uniform tool rather than three separate manual processes, giving stakeholders and reviewers a consistent, future-proofed view as KPIs change over time — with the added Thresholds table giving full traceability from RAG status back to the underlying rule and consequence.
